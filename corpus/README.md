# Northbridge Analytics Policy Corpus

This folder is the RAG source corpus for the Group Project 3 agentic HR
system. It describes the fictional company **Northbridge Analytics, Inc.**
(a Chicago-headquartered data/analytics consulting firm) and its HR
policies and procedures. All content is synthetic and written for this
project; it is not a real company.

## Contents

- `policies/` — 12 policy documents in three formats (markdown, HTML, plain
  text), totaling ~16,300 words / ~32.5 pages at a 500-words-per-page
  estimate (see `manifest.json` for the exact per-document word count).
- `manifest.json` — machine-readable index of every document: `doc_id`,
  `title`, `filename`, `format`, `version`, `effective_date`, `owner`,
  `applies_to`, word/page counts, and the list of numbered `sections`
  (`section_id` + `heading`) parsed directly out of each file. This is the
  intended source of the citation metadata required by the project spec
  (document title/ID, section, source snippet) — ingestion code should
  treat this file as authoritative rather than re-deriving titles or
  owners by scraping prose.

## Conventions for ingestion

- **Section IDs are the citation unit.** Every document is broken into
  numbered sections such as `PTO-3` or `RW-4` (pattern: `DOC-CODE-N`).
  Chunking should be heading-aware and should preserve the section ID in
  chunk metadata — it's the stable identifier the mock data and the
  cross-document scenarios below reference, and it's what the RAG
  guardrail-facing citations (document ID, section) should surface.
- **Cross-references use section IDs**, e.g. "see PTO-8" or "per TAX-5".
  These are a deliberate feature: several evaluation questions require
  retrieving from more than one document (see the multi-document example
  below), and the cross-references are how a human reader — and how a
  retriever using them as anchor text — finds the related section.
- **Frontmatter/metadata carries doc_id, version, effective_date, owner.**
  Markdown files use YAML frontmatter; HTML files use `<meta name="...">`
  tags; the one `.txt` file (`LEAVE`) uses a `KEY: value` header block.
  `manifest.json` normalizes all three into one schema.
- **At least two source formats** are represented (markdown, HTML, and
  plain text), satisfying the ingestion requirement to handle more than
  one format.

## Scenarios the corpus was written to support

The corpus was deliberately built so two things are true at once: single
policy documents answer simple questions, and several realistic questions
require combining two or more documents (per the project's requirement to
include at least one complex, multi-document question). For example:

- **Remote work eligibility (international, extended).** "Can I work from
  Portugal for six weeks?" requires REMOTE-WORK-4 (international exception,
  20-business-day cap) *and* TAX-5 (why the cap exists) *and*, for the
  security review, INFOSEC (SEC-3/SEC-4) — a genuine multi-document
  question with a clear, checkable answer (not approvable as a standard
  exception; see `mock_data/hr_tickets.json` ticket `TCK-10021` for a
  live example of an employee hitting exactly this limit).
- **PTO request guidance.** "Can I take 3 days off next week?" requires
  PTO-2/PTO-3 plus the employee's actual balance in
  `mock_data/pto_balances.json`.
- **Expense compliance.** "Can I get reimbursed for a personal laptop?"
  requires EXP-3 and the equipment-vs-expense boundary in EQUIPMENT.
- **Benefits triage.** Eligibility questions route through BEN-1/BEN-7 and
  the employee's `employment_type` in `mock_data/employees.json`.

See `mock_data/README.md` for how the structured data lines up with this
corpus (consistent state list, consistent accrual arithmetic, etc.).

## Regenerating `manifest.json`

`manifest.json` was generated by parsing the section headers and
frontmatter/meta tags out of the files in `policies/` (see the project's
`ai-tooling.md` for the generation approach). If a document's content or
version changes, regenerate the manifest rather than hand-editing it, so
word counts and the section list stay accurate.
